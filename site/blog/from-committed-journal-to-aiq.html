From a committed .journal to aiq

Before aiq was a tool, it was a protocol document — 367 lines of prose asking language models to be perfect clerks. This is what a Markdown ledger inside an Arduino curriculum project taught us, and why the second system is a SQLite file with a contract.

Chat is a cache

AI coding agents forget. Every session starts cold; every compaction throws away the middle of the story; every parallel sub-agent knows only what its prompt carried in. If you use agents for sustained work on a real project, the question is not whether to give them durable memory but where that memory lives and who gets to write it.

Our first serious answer grew inside an unlikely host: a private Arduino curriculum project with dozens of hardware lessons, strict verification gates, and more concurrent agent work than any one context window could hold. The project needed agents that could stop mid-task, hand off, recover, and not drop a single obligation across weeks of sessions. So it got a committed .journal/ directory — every agent's operational memory, tracked in Git alongside the code.

The first system: a ledger made of prose

The .journal/ protocol was earnest and thorough. Every user message became an immutable event, classified into one of six kinds. Every task got a UUID-named subtree with its own state file, event log, and decision log. A lock directory with an owner.json — lock UUID, agent UUID, PID, hostname, boot ID — coordinated writers. Leases were committed files. Defect reports about the journal itself went through a feedback subsystem with immutable reports, scheduled reviews, and superseding dispositions. Before an agent was allowed to stop, a yield-check guard re-read every ledger and demanded a reconciliation of live agents, capacity, and unassigned lanes.

It worked. Multi-agent sessions shipped review after review; the work queue held; recovery from a cold start was a documented loop rather than an improvisation. And the whole time, the protocol was teaching us — mostly by what it cost.

What the prose ledger taught us

State in the worktree pollutes the work. A committed journal rides in every diff, merge, and branch. Agent bookkeeping and user code fought over the same commits, and "never capture, stash, or rewrite pre-existing user changes" had to be legislated because the layout made it possible to violate.

A prose protocol grows without bound. Every edge case became another paragraph an agent must re-read at every boundary. The protocol document reached 367 dense lines — a real context tax per session, paid before any useful work began — and it was still incomplete, because prose always is.

Discipline you cannot check is discipline you do not have. The yield guard required agents to supply their own capacity counts, and the document admitted the flaw out loud:

These capacity arguments are a procedural attestation, not machine-derived proof… The consistency checks catch omissions and impossible totals but do not authenticate self-reported values.

A probabilistic reader following a prose contract will eventually misfile an event, skip a re-read, or hold a lock through an operation the protocol forbade. None of that is malice; it is what happens when the ledger's invariants live in the reader instead of the medium.

Liveness heuristics are quicksand. "PID alone does not prove liveness. Check environment, process-start identity, runtime ownership, and Git/journal progress." Every word of that is correct, and every word is a symptom: the storage had no transactions, so the protocol had to reinvent them socially.

The second system inverts the decisions

aiq is the same set of motives — never spend a scarce resource twice; codified answers repeat, re-derived ones drift — rebuilt with the opposite design choices at every point the first system hurt.

The .journal protocolaiq
Committed Markdown tree in the worktree Private SQLite journal beside Git's metadata (.git/aiq/), never committed
367 lines of prose re-read at every boundary Versioned capability contracts, loaded one at a time on demand
Messages classified into six kinds at capture Exact capture first; interpretation deferred until a worker claims the message once
Lock directory plus PID-liveness heuristics Time-bounded leases with owner and fence; an expired claim authorizes nothing
Rebuildable queue.md, "never authoritative" Readiness derived from the dependency graph; there is nothing to rebuild
Task edits as prose state files One atomic effects document per message, with expected revisions — stale writes fail whole
Yield-check fed by self-attested counts A Stop-gate hook that counts ready tasks, live claims, and unapplied messages mechanically
An in-repo journal.py helper An installed, installer-neutral CLI with stdlib-only runtime

The through-line: move every invariant out of the reader and into the medium. An agent cannot misfile an event it never classifies, cannot corrupt a queue that is derived rather than maintained, and cannot complete stale work when the storage refuses the write.

What the ledger looks like now

message → claim → atomic effects → versioned tasks → ready queue → lease

A message is captured exactly and hidden from casual listing; reading content is a deliberate act tied to a claim. Applying a message produces one all-or-nothing effects document; identical retries replay the stored result, conflicting retries fail. Tasks are projections of immutable revisions; dependencies drive readiness; leases fence concurrent workers and expire on their own.

The recent work has been about closing the loop with the agents themselves:

  • Hook integrations for Claude Code and Codex capture every user prompt into the journal before work begins, and gate session stop on runnable work — the yield-check idea, reborn as something the machine verifies. The installers are reversible, ownership-recorded, and drift-checked; hooks run Python with -I so no environment variable can redirect them.
  • Health as a contract: aiq doctor summarizes configuration, journal, scope, and integration state read-only, and names the remedy next to each finding; aiq reconcile --user re-verifies everything after an upgrade.
  • Self-reporting: aiq report files a defect from any repository as a deduplicated bug-fix task in aiq's own development queue — the tool's issues are tracked by the tool.
  • Introspection without content: aiq status, task explain, task history, and claim list answer the questions agents actually ask at scheduling boundaries, in bounded deterministic output.

One detail we are fond of: this post was itself queued, leased, and completed through the ledger it describes, with the Stop gate refusing to let the session end while the work was still open.

What aiq refuses to do

No server, no account, no telemetry, no cross-machine sync, no model calls, no execution of the work it tracks. Those are not roadmap gaps; they are the boundary that keeps a work ledger trustworthy. State lives on your machine, beside your repository, in a format you can snapshot, export, and verify.

aiq is alpha. The human-facing surfaces may still move; the machine contracts — CLI JSON envelopes, effects documents, capability descriptors, integration manifests — carry their own explicit versions precisely so agents can depend on them while everything else improves.

Try it

Note added 2026-07-30: this post describes aiq as it stood on the day it was published, and the commands below are the ones it shipped with. Since then the recommended install is a pinned release tag — @main is the development channel, which changes without notice — and hook capture became opt-in per repository, which the journal init --scope repo below already does. The README has the current install.

pipx install 'aiq-workqueue @ git+https://github.com/spincyc/aiq.git@main'
aiq journal init --scope repo
aiq ingest --message "Queue this work"

The repository has the full documentation: concepts, configuration, privacy, recovery, and the integration contracts.
